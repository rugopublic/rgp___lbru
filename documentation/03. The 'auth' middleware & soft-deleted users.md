# Как включить soft-deleted пользователей в middleware аутентификации

## Контекст проблемы

В стандартном Laravel-пайплайне middleware `auth` работает через guard и `Auth::check()`. Это означает:

* guard извлекает пользователя **без `withTrashed()`**
* soft-deleted пользователь считается *неаутентифицированным*
* происходит редирект на маршрут логина (`/login`)

Это поведение корректно для большинства приложений, но **ломает юридически корректный flow удаления аккаунта**, где:

* пользователь уже soft-deleted
* но всё ещё должен иметь доступ к:

    * странице `pending`
    * отмене удаления
    * информационным экранам

---

## Почему `Auth::check()` недостаточно

```php
Auth::check(); // false для soft-deleted пользователя
```

Причина:

* Eloquent global scope `SoftDeletingScope`
* guard не умеет `withTrashed()`
* пользователь не поднимается из БД

Следствие: middleware `auth` не подходит для этого сценария.

---

## Архитектурное решение

Ключевой момент: **был создан кастомный Auth User Provider**, который умеет извлекать пользователя с учётом `withTrashed()`.

То есть поддержка soft-deleted пользователей реализована **на уровне провайдера**, а не хаками в middleware или guard.

Подход:

1. Стандартный `auth` продолжает отвечать за наличие сессии
2. Кастомный provider возвращает пользователя даже если он soft-deleted
3. Дальнейшая логика доступа выносится в доменные middleware

Это позволяет:

* сохранить совместимость со стандартным `auth`
* корректно работать с soft-deleted пользователями
* избежать переопределения `SessionGuard`

---

## Middleware: EnsureUserIsSuspended

Используется для страниц:

* deletion pending
* confirmed
* cancel deletion

Ключевая идея:

* пользователь уже залогинен (session есть)
* но модель может быть soft-deleted

Проверка строится на `$request->user()`.

```php
public function handle(Request $request, Closure $next)
{
    $user = $request->user();

    if (!$user || !$user->trashed()) {
        return redirect()->route('user.account.index');
    }

    return $next($request);
}
```

---

## Middleware: EnsureUserIsNotSuspended

Используется для:

* профиля
* редактирования
* инициации удаления

```php
public function handle(Request $request, Closure $next)
{
    $user = $request->user();

    if ($user && $user->trashed()) {
        return redirect()->route('user.delete.pending');
    }

    return $next($request);
}
```

---

## Важный вывод

* `auth` отвечает **только за наличие сессии**
* состояние аккаунта — ответственность **доменных middleware**
* soft-delete ≠ logout

Это позволяет:

* сохранить юридически корректный UX
* не ломать стандартные механизмы Laravel
* избежать хака guard'ов и provider'ов

---

## Антипаттерны (чего не стоит делать)

❌ Переопределять `auth` middleware

❌ Лезть в `Illuminate/Auth/SessionGuard`

❌ Делать кастомный guard ради soft-delete

❌ Использовать `withTrashed()` глобально

---

## Резюме

Soft-deleted пользователь — это **не гость**, а пользователь в особом состоянии.

Laravel даёт все инструменты, чтобы корректно это выразить — через отдельные middleware.

Так архитектура остаётся чистой, а flow — прозрачным и безопасным.
